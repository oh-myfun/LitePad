## B60（同日续）用户反馈三项：分隔条改细 / 落点回退浅蓝 / 对齐联动

### ① 分隔条「粗」的根因是占位，不是线宽

排查：`.layout-sep` 是 `flex: 0 0 7px` 的**透明占位**，线本身只有 2px，但 7px 空档把两侧
内容撑开、露出祖先底色 —— 标签栏行上两侧是 `--bg-status`，中间这 7px 是 `--bg`，
色差就成了一条粗带。VS Code 的 sash 是 absolute 浮层、**完全不占位**（`sash.css`，
`--vscode-sash-size: 4px`），所以边界永远只是一条细线。

改法（`global.css` 的 `.layout-sep*` + `preview.css` 的 `.toc-resizer`，B28 同款）：
- 元素 `flex: 0 0 0` —— ⚠️ 只把**主轴**清零；交叉轴仍 `stretch` 成满长，所以
  `.layout-sep-h::before`（竖线）能写 `top:0;bottom:0`、`.layout-sep-v::before`（横线）
  能写 `left:0;right:0`。这点一开始差点想岔。
- 7px 命中区搬到 `::before`，向两侧各溢出 3.5px，压在相邻面板之上（B53 的宽命中区保留）。
- 视觉线 `::after`：静息 1px（VS Code `editorGroup.border` 就是 1px）→ 悬停/拖拽/联动 4px。
- 角手柄从「贴着 7px 带摆」（`top:0`/`left:0` + 7px）改成**骑在界线上**（`-4px` + 8px），
  否则分隔条主轴尺寸变 0 后手柄会整块偏到一侧。

### ② 落点回退浅蓝

`--drop-fill` 回到 accent @0.22（深 `#4c9ffe` / 浅 `#0969da`），`::after` 加回
`border: 2px solid var(--drop-fill)` + `border-radius: 4px`。描边压在填充上叠加成约

### ③ 对齐联动（linkedSash）

上游取证（本地 `docs/vscode-reference/`）：
- `gridview.ts:715-722` `trySet2x2`：两个 2 子节点分支 + 首子尺寸相等 → 互为 `linkedSash`。

## B60 二次反馈：联动真机没生效（已修）+ 预览不要描边

### 联动「还是没法一起拖动」= `centerOf` 用主轴判空

`centerOf()` 原写 `len = dir === "h" ? r.width : r.height; if (!(len > 0)) return null;`
—— 但 ① 把分隔条改成 `flex: 0 0 0` 的浮层后，**主轴尺寸恒为 0**。于是 `len` 永远 0、
`centerOf` 恒 `null`、`alignedSashesOf` 永远空数组：**联动在真机上从没生效过一次**。
（vitest 全绿是因为用例把 rect 桩成 4px 宽 = B60 之前的几何，桩比现实「宽松」就把 bug 盖住了。）

修：改看**交叉轴** `cross = dir === "h" ? r.height : r.width`（stretch 出来的满长，
> 0 才说明浏览器真摆了盘）；主轴为 0 恰好意味着 `left`/`top` **就是**界线，直接取用。
这个判据同时挡住「全零被当成都在 0 点」的误判（新增用例锁住）。

顺带确认：像素判据与 VS Code `trySet2x2`（要求两分支 `getChildSize(0)` 相等）在两行等宽时
**等价** —— 所以「同向 + 位置差 ≤ 2px」既合用户说的「位置一致」，也不漏 VS Code 会联动的场景。

⚠️ **通用教训（已写进 ARCHITECTURE）**：测试桩必须忠实于真实几何。**改几何的改动，
务必回头核对 test 里的 rect 桩。** 反向验证：把 `centerOf` 改回主轴判空 → 4 条联动用例全挂；
修回 → 全绿。

## B62 双击复位要「整组居中」（用户反馈）+ 顺带修掉「点一下就拆散联动」

用户原话：「分割条联动时双击任意一条，所有的都应该居中。」

### 根因 A：联动集合在改比例**之后**才求（次序 bug）

老 `dblclick` 先 `for (targets) applyTarget(t, 50); commit(0.5)`，
**之后**才 `alignedSashesOf(handle, mode)`。而后者经 `centerOf` →
`getBoundingClientRect` 读的是**实时几何** —— 本条已挪到 50%、联动条还停在 30%，
两者差几百 px ≫ `ALIGN_TOL = 2px`，集合恒为空 → 只有点中的那条居中。
**修：先把集合取出来，再统一改比例。**

### 根因 B（顺带）：纯点击也会回写比例，一次点击就拆散对齐

`onUp` 无条件 `commit(pctFor(指针))`。命中区 7px 宽，指针常离界线几个像素，
一次「点一下」就能把比例推走约 1%（400px 容器 ≈ 4px），而对齐容差只有 2px ——
**点一下两条对齐的线就出了容差，之后拖谁都不再联动**（「联动时灵时不灵」的真凶之一）。
VS Code 的 sash 同样是「没有 move 事件就不改尺寸」。
**修：`mousedown` 记 `moved`，只有真收到 `mousemove` 才在 `onUp` 回写。**

### ⚠️ 测试教训（第二次栽在同一个坑上）

这两个 bug 都被「**常量 rect 桩**」掩盖：常量几何里，先把本条挪到 50% 后桩仍说两条同位置；
纯点击也照样按桩算出一个不同的比例却没断言。
现在 `tests/splitview.test.ts` 的 `stubVerticalSash()` 读**左栏的 inline flexBasis** 实时算
界线位置，忠实于浏览器。反向验证：两处修复分别还原 → 对应用例各自失败。

regressions 的 B60 静态块改为断言 `alignedSashesOf` 出现在 `applyTarget` **之前**。

## B63 交叉点联动 + 双击按分割数量均分（用户反馈）

用户原话：「在交叉点拖动时，也要支持联动（高亮和一起拖动）。分割条双击不一定是居中，
而是根据分割数量均分（对应的所有分割线一起调整）。」

### ① 交叉点也要联动：把「一起动的那组」收成一个入口

B60 的联动只认「同向 + 位置一致」，且角手柄被显式排除（`mode === "corner" ? [] : …`）。
但角手柄恰是**轴互相垂直的两条线的交点**，它一次拖两条，这两条各自还可能有同向伙伴
（2×2 网格里，交叉点一拖 → x 轴两条竖线 + y 轴那条横线，**三条**一起动）。
新增统一入口 `movingGroupOf(targets)` = 每个目标自身 + 与它同向对齐的伙伴；
`mouseenter` / `mousedown` / `onMove` / `onUp` **四处全走它**（四者不统一就会出现
「高亮了一组、实际只动了一条」）。

⚠️ **角手柄必须复用子分隔条已注册的 `ResizeTarget` 对象**：
`attachResize(cHandle, [self, child.target], "corner")`。注册表按 **target 身份**
（`sashOfTarget`）查伙伴，另造对象会让查找落空 → 子轴一侧的联动**静默失效**。
为此 `BuiltNode.split` 新增 `target: ResizeTarget` 字段把注册对象带出来。

### ② 双击不再一律 50%，而是按分割数量均分

同轴链：`chainId`（与父同向则沿用父的链号），`segmentsAlong(node, d)` 数出沿轴的段数，
`equalRatio = segA / (segA + segB)`。

| 段数 | 逐级比例 | 各格实际占比 |
| --- | --- | --- |
| 2 | 1/2 | 50 / 50 |
| 3 | 1/3 · 1/2 | 33.3 / 33.3 / 33.3 |
| 4 | 1/4 · 1/3 · 1/2 | 25 / 25 / 25 / 25 |

望远镜式相乘：第 k 级拿 1/(n−k+1)，剩余交给下一级，乘完每格都是 1/n。
双击时 `chains = new Set(movingGroupOf(targets).map(s => s.chainId))`，
把**整条链**（含各条的联动伙伴）一起调 —— 同轴链 + 跨行的对齐条都覆盖到。

## B64 标签拖拽要有跟随光标的浮动影像（用户反馈）

用户原话：「标签拖动时，要像 vscode 那样有一个 tab 随光标移动的效果。」

### VS Code 的事实（读源码）

`multiEditorTabsControl.ts:1265-1300` 的 `onDragStart`：
- 拖**单个**标签且 `tabSizing !== 'shrink'` → `e.dataTransfer.setDragImage(tab, 0, 0)`，
  注释写明「把被拖标签的**左上角**放到光标处，好给落点边框反馈让位」；
- 多选、或 `shrink`（标签可能被裁剪）→ `applyDragImage(e, tab, label)`，即
  `base/browser/ui/dnd/dnd.ts` 的 `.monaco-drag-image` 纯文字药丸（`setDragImage(img, -10, -10)`，
  `max-width: 120px`、`z-index: 1000`、`outline: 1px + offset:-1px`）。

本项目标签是 `tabSizing: fixed`（B56 起不收缩、不裁剪）→ 正落在**第一档**：影像 = 标签元素本身。

### 实现

拿不到浏览器影像（指针事件自编排拖拽，WebView2 原生拖放钩子禁用了页面内 HTML5 DnD），
所以自己做 `.tab-drag-ghost` 浮层：
- `createDragGhost(tabEl)`：`cloneNode(true)` 克隆整个标签（图标/文件名/未保存点/配色一并带过来），
  挂在 `body` 上（fixed 定位）。
  ⚠️ 剥掉副本的 `data-tab-id`（否则「按 tabId 查元素」会命中副本）与 `data-tip*`；
  `button` 置 `tabIndex=-1`（外面套着 aria-hidden）。
- 锚点 = 左上角：`left/top` 直接写 `clientX/clientY`（JS 里就一句注释指回
  `setDragImage(tab, 0, 0)`）。
- **越过 `DRAG_THRESHOLD` 才创建**（纯点击不该闪出一个副本）。
- 跟随调用必须放在「离开面板就 `return`」**之前** —— 拖到面板之外影像也得跟着走，
  否则会僵在最后一个面板上。
- 原标签**原地不动**（和 VS Code 一样，它是判断「拖到哪儿了」的参照物）。

### 顺手补的一个真 bug：拖出窗口会留下幽灵

拖到窗口外松手，`mouseup` 收不到 → 原先只是「拖拽态卡住」（无影像时不明显），
现在会留下一个跟不动的浮动标签。加 `window` 的 `blur` → `finishTabDrag()`（失焦即取消），
`finishTabDrag` 里同步 `removeEventListener` + `removeDragGhost()`。

### 与 VS Code 的有意偏离（一处）

原生影像是元素快照，非活动标签的底色本就透明；我们的浮层要盖在编辑器/预览上，
透明底会糊成一片 → 补 `--bg-elevated` 底色 + 内侧描边 + 阴影。
描边用 `outline` + `outline-offset: -1px`（照搬 `.monaco-drag-image` 的写法）而不是 `border`
—— 后者会撑大盒子，影像就比真标签大一圈。浅色主题是白影压白编辑区，没这圈线几乎浮不起来。

### 沙箱内的观感验证（新姿势，已记进 BUILD-ENV.md）

## B65 标签上的 ● 与 × 不得同时显示（用户反馈）

用户原话：「标签上的关闭图标 x 和修改未保存图标原点不要同时显示，包括鼠标 hover 和拖动时。」

### 根因：互斥只做了 `:hover` 一档

`.tab-action` 是一个固定尺寸槽位，里面 `.tab-mark`（●）与 `.tab-close`（×）都常驻 DOM，
靠 `opacity` 二选一（B57）。B57 写的是两条规则：

```
.tab-dirty .tab-mark { opacity: 1 }                 /* ● 无条件常驻 */
.tab:hover  .tab-mark { opacity: 0 }                /* 悬停时让位 */
.tab:hover / .tab-active / .tab:focus-within .tab-close { opacity: 1 }
```

× 有**三个**出场口，而「压回 0」只补了 `:hover` 这一档 → 剩下两个口上两个 glyph 双双
`opacity: 1`，叠死在同一个槽位里（观感 = 一个带橙调的 ×）：

1. **未保存的当前标签**（最常见）：必然同时带 `.tab-dirty` 与 `.tab-active` → 打开一个
   改过的文件就一直是这样，不需要任何鼠标操作；
2. **键盘把焦点落到标签上**（`.tab:focus-within`），同样不经过 `:hover`；
3. **B64 的拖拽影像**：克隆的就是活动标签，副本 `pointer-events: none` 永不 `:hover`
   → 拖「未保存的当前标签」时副本里也叠着。

还有一处同源的病：`.layout-panel:not(.layout-panel-active) .tab-close { opacity: 0.5 }`
（B57 写成了**无条件**）。后果之一是非焦点面板里**每个**标签常驻一个 50% 的 ×
（VS Code 非活动组的 × 同样只在悬停/活动/聚焦时出现，只是暗一档）；
后果之二就是 B65：未保存标签的 ●（1）跟这个常驻的 ×（0.5）叠在一起。

### 修法：把「互斥」收进一条 `:not()` 链

```css
.tab-dirty:not(:hover):not(.tab-active):not(:focus-within) .tab-mark { opacity: 1; }
```

- 条件写全在**一条**规则里，而不是再补三条「压回 0」——后者与 `.tab-dirty` 那条**同特异度**，
  只能靠源码顺序取胜，日后调整样式表顺序就静默失效。
- 与 VS Code 同构：上游是单 glyph + `.action-label:not(:hover)::before` 换内容
  （`multieditortabscontainer` 那套），等价于「● 只在 × 不出场时出场」。
- 非焦点面板的降亮度改成**逐条对齐三个触发口**：
  `.layout-panel:not(.layout-panel-active) .tab:hover|.tab-active|.tab:focus-within .tab-close { opacity: 0.5 }`。
  特异性 (0,4,0) 压过上面那组 (0,3,0)/(0,2,0)，与源码顺序无关。
  焦点感仍由「同样命中时更暗」保证（两块面板都悬停/都是活动标签时 0.5 vs 1）。

- 改后：前两处是干净的 ×、`b.txt` 是干净的 ●、`c.txt` 什么都没有，影像里也是干净 ×。

## B66 未保存标签默认 ●，只有指针进关闭区才换 ×（用户反馈）

用户原话：「未保存标签存在时，默认显示未保存标签，只有鼠标放到关闭按钮区域时才变成关闭图标。」

### 先核上游：这就是 VS Code 的语义

`multieditortabscontrol.css:491`（经典档）：
`.tab.dirty > .tab-actions .action-label:not(:hover)::before { content: circle-filled }`
—— 判据是 **action-label 自己的 `:hover`**（= 关闭区 16+2×2 = 20px 的盒子），不是整个标签。
现代档不用 CSS，但 `multiEditorTabsControl.ts` 的 `redrawTabSelectedActiveAndDirty` 只切
`dirty` / `active` 类，换装仍由上面这条 CSS 完成（全文搜索 `codicon-close` 无命中）。
所以「未保存 → 平时 ●，指针进关闭区才 ×」不是新设计，是把 B57 漏掉的那一档补回来。

### 改了什么

`×` 的出场口从「三个」重排成**四个，按保存状态分档**：

```css
.tab-action:hover .tab-close,              /* ① 关闭区命中 —— 脏标签的唯一换装口（B66 新增） */
.tab-action:focus-within .tab-close,       /* ② 键盘落到关闭键上（同上） */
.tab:hover:not(.tab-dirty) .tab-close,     /* ③ 已保存：悬停标签（B57 原行为） */
.tab-active:not(.tab-dirty) .tab-close {   /* ④ 已保存：活动标签常驻 ×（B57 原行为） */
  opacity: 1;
}

.tab-dirty .tab-action:not(:hover):not(:focus-within) .tab-mark { opacity: 1; }
```

三个要点：

1. **判据必须挂在 `.tab-action` 上，不能挂在 `.tab` 上** —— 挂到标签上就成了「指针划过
   文件名 ● 就消失」，与用户要的「放到关闭按钮区域才变」不符。反向断言锁住这条。
2. **③④ 必须带 `:not(.tab-dirty)`** —— 否则脏标签的活动标签会常驻 ×，既顶掉 ●（B65 的老病）
   又与本次要求冲突。已保存标签保留 B57 的「活动标签常驻 ×」（关闭当前文件是高频操作）。
3. `:focus-within` 从 `.tab` 挪到 `.tab-action`：标签元素本身没有 tabIndex，槽位里唯一可聚焦的
   是关闭按钮，两者等价而后者语义更准。

连带：**非焦点面板的 × 降亮度必须同步补上新增的两档**（`.layout-panel:not(.layout-panel-active)
.tab-action:hover/:focus-within .tab-close { opacity: 0.5 }`）。这个「触发口要对齐」的坑
B65 已经踩过一次，这次是第二次 —— 已写进 `ARCHITECTURE.md` 并加了注释警告。

顺带解决了 B65 留的那个待定项：**B64 的拖拽影像现在稳定显示 ●**（副本永不 `:hover`，
命中不了关闭区 → 走 ● 那条），不再是「拖未保存标签时影像显示 ×」。

### 验证：这次把 `:hover` 也量出来了

## B68 预研（0917）：热退出（Hot Exit）——用户要「自动保存写副本 + 关窗不弹窗 + 下次恢复」

**用户原话**：「自动保存功能并不是真的保存修改到打开的文本，而是保存一个副本，这样就算是存在未保存状态时
关闭窗口，也不用弹窗确认，下次打开应用还能恢复到未保存的状态。vscode也有这个能力，看下是否也是用的这个方案？
告诉我vscode的方案让我选择。」

**结论**：用户描述的三件事（写副本 / 关窗不弹窗 / 下次恢复未保存态）= VS Code 的 **Hot Exit**，
**不是 Auto Save**。VS Code 两个机制各自独立、可同时开。

### 上游取证（commit `632abec535785c5fd76dec5b8ceb2f4c53d8cfc3`，下到 `%TEMP%/vscode-hotexit/`）

  另有两个附加限制 `autoSaveWorkspaceFilesOnly` / `autoSaveWhenNoErrors`（都默认 false）。
- `files.hotExit`（:123，仅 native 分支）：`off` / `onExit` / `onExitAndWindowClose`，**默认 `onExit`**（:128）。
  ⚠️ `hotExit.off` 的官方枚举说明原文就是答案：
  "Disable hot exit. **A prompt will show** when attempting to close a window with editors that have unsaved changes."
  → **「关窗不弹确认框」是 Hot Exit 的职责，不是 Auto Save 的**。
  `onExit` 说明还写明：无文件夹的窗口下次启动自动恢复；带未保存文件的窗口列表在 `File > Open Recent > More...`。

  → **按资源哈希命名，不沿用原文件名**；scheme 那一级区分本地文件 / untitled。

## B68 交付（0917）：热退出 + 顺带修好 M4 大文件降级

### 一个关键澄清（决定了整个设计）

「参考 vscode」的恢复方式落到 LitePad 上其实**只剩一种**：VS Code 是
「无文件夹的窗口下次启动自动恢复；有文件夹的窗口才进 `File > Open Recent > More...`」，
而 **LitePad 没有工作区/文件夹概念**（`grep -rn "workspace|folder" src src-tauri/src` 零命中）。
`WorkbenchState.EMPTY` 恒成立 → **一律静默自动恢复**。
推论：`files.hotExit` 的 `onExit` 与 `onExitAndWindowClose` 两档在本项目**无法区分**，
所以合并成布尔开关 `hot_exit`（开 / 关），并在注释里写明为什么不是三态。

另一个上游事实（决定「什么时候写副本」）：VS Code 的备份**不是关窗时才写**，
而是 `WorkingCopyBackupTracker` 里 `onDidChangeContent` / `onDidRegister` / `onDidChangeDirty`
三处都 `scheduleBackup()`（防抖），关窗只是「等它兑现」。
好处是强杀进程也能捞回未保存内容。LitePad 照抄了这个节奏（`scheduleBackup()` 1s 防抖）。

### 环境教训（已写进 BUILD-ENV.md）

⚠️ **同一文件的两处编辑绝不能并发**：编辑是「读—改—写」，同文件并行两个请求时后写的
会覆盖前一次，而**两次都回报成功**。本次一次编辑请求里对 `session/mod.rs`、`commands/mod.rs`、
`main.rs` 各发了两处改动，结果三处「字段/命令/注册」里各丢了一半，
编译报「没有 hot_exit 字段」这种看着莫名其妙的错。**同文件串行、跨文件才并发**。

### 收尾：提交前复核又逮到一个跨面板 bug

提交前逐行复核 `restoreSession`，发现预取缓存的键写成了 `` `${i}|${identityOf(st)}` ``
（**面板索引 + 文档身份**）。这看起来更「精确」，实际是错的：
`restoreBackup()` 每调一次就**新建一个标签**，所以同一个文件在两个面板打开时，
会在两个面板各预取一次 → 恢复出**两份互不同步的文档**，
把项目的核心不变量「同源多实例」悄悄破坏掉。

修法：键只用 `identityOf(st)`（有 path 用 path，未命名的用 `#<backupId>`），
同一文档全局只预取一次，逐面板恢复时各自 `makeInstance` 复用同一个 doc。

⚠️ **反向验证**：把键改回带面板索引的形式，**9 条用例立刻变红**
（其中 8 条是 smoke 里会重复建实例的用例）。这说明守卫是真的，不是摆设。
