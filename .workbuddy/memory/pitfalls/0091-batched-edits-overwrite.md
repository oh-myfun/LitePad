# ADR 0091：同一条消息里的多个 Edit 会**互相覆盖**，但每个都回报成功

- **状态**：Accepted（09-21 一次会话内实测两处丢失）
- **域**：工具链 / 沙箱
- **来源**：B91（改 `dropbridge.rs` 时 4 处修正只落 1 处；改 `main.rs` 时 2 处只落 1 处）
- **关联**：`MEMORY.md` 红线「编辑回报成功 ≠ 已落盘」的同一族（那条讲的是「写了没生效」，
  这条讲的是「**写了但被同批的另一个编辑覆盖**」）；`pitfalls/0082`、`0083` 同族（静默丢失）

## 背景（Context）

B91 第一次 `cargo check` 报 3 个错（借用、类型、unsafe）。我把 3 处修正 + 1 处返回值改动
**放在同一条消息里**发了 4 个 Edit，工具对 4 个都回了 `Successfully edited file`。
重跑 `cargo check` —— **报的还是原来那 3 个错**，日志里连行号都是旧的。

回读文件才看清：4 处修正只有最后一处（`path.to_string()` 的 unsafe 包装）在文件里，
其余 3 处原样未动。同样的现象当天又出现一次：给 `main.rs` 加 `mod dropbridge;` 与
`dropbridge::install(...)` 调用（同一条消息两个 Edit），第一个落了、第二个没落 ——
`mod` 声明在、调用不在，`cargo check` 不会报错（函数没人调用而已），**只能靠回读发现**。

## 根因（Root Cause）

**多个 Edit 在同一批里对同一文件并发执行，各自读到同一份旧快照、各自整文件写回，
最后一个写入者胜出，其余修改被静默丢弃。** 与内容、匹配唯一性、文件大小都无关 ——
不是「没匹配上」（那样会报错），而是匹配上了、改了、然后被覆盖。

判据（今天拿到的两次观测完全一致）：

- 工具回报**全部成功**，退出码正常，没有任何警告；
- 落盘的是**其中一个**编辑的结果，其余编辑像是从未发生；
- 跨文件的批量编辑没出过问题（`Cargo.toml` + `main.rs` + `windows.rs` 同批：三个文件都改到了，
  其中 `main.rs` 丢的是**同批里针对它自己的第二个**编辑）。

## 决策（Decision）

1. **同一文件，一条消息只发一个 Edit。** 需要改多处时，一条一条来（或改用 Write 整文件重写）。
2. **跨文件批量编辑照旧**（实测安全）：不同文件的编辑互不影响，可以同批提交。
3. 改完**必须逐处回读**，而不是只看工具回报：`grep -n` 关键片段（函数签名、调用点、
   常量值），确认每一处都在。B91 里正是靠「`cargo check` 报的还是旧行号」+ `grep` 才发现的。
4. 与 `MEMORY.md` 那条红线合并理解：**Edit 的回报只代表「匹配上了」，不代表「文件现在是你要的样子」。**

## 后果与守卫（Consequences）

- 代价：多花几轮工具调用；换来的是「改完即确认」，不再出现「以为改了、其实没改」的调试黑洞。
- 与本项目其它静默失效（`git checkout --` 不落盘、钩子写了不生效）归为同一类：
  **凡是「工具说成功」的地方，都要有一处回读作证**（`pitfalls/0074`、`0083` 的教训同构）。
