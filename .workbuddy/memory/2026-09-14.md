## B48 安装包缺 WebView2Loader.dll → 装好的应用起不来（紧急）

用户原话：安装包缺少 dll，导致安装好的应用无法启动。

- **现象定位**（三步，全部可在沙箱内完成，无需装到系统）：
  1. `objdump -p litepad.exe | grep -i "DLL Name"` → exe 只依赖系统 DLL + **`WebView2Loader.dll`**
     （Tauri 的 WebView2 加载器，**必须与 exe 同目录**，缺了进程起不来）。
     好消息：gnu 工具链下**没有** libgcc_s_seh-1 / libwinpthread-1 依赖，不用静态链接方案。
  2. `7z l LitePad_0.2.0_x64-setup.exe`（7z 在 `/c/Users/maoyu/scoop/shims/7z`，能识别 NSIS 包）
     → 包内 7 个文件里**只有 litepad.exe**，没有这个 dll。
  3. dll 本体在 `src-tauri/target/release/WebView2Loader.dll`（构建期生成），
     但 **bundler 不会自动把它收进包**——这就是漏掉的原因。
- **修复**：`tauri.conf.json` 的 `bundle.resources` 用 **map 形式**显式声明
  `{"target/release/WebView2Loader.dll": "WebView2Loader.dll"}`，
  把它打到**安装目录根**。必须 map：字符串形式会沿用 `target/release/` 子路径，exe 仍找不到。
- **验证**：① 重新 `tauri build` 后 `7z l` 显示包内 8 个文件、根目录含该 dll；
  ② 复制 exe + dll 到**干净临时目录**启动，进程存活 5s（精确模拟安装后布局，避免
  target/release 里其他文件"帮忙"导致假通过）。
- **回归**：`tests/regressions.test.ts` 新增断言 bundle.resources 必须把该 dll 打到根目录
  （两种写法都认：数组 / map；且目标不得带子路径）。
- 因 v0.2.0 的安装包不可用，已 bump 到 **v0.2.1** 并推 tag（`release.sh patch --ci`）。

### 追加坑：第一版修复在本地"假通过"、CI 冷构建失败

- 第一版把 resources 指向 `target/release/WebView2Loader.dll`：本地打包正常（target 里有旧残留），
  **CI 冷构建直接失败**：`resource path target\release\WebView2Loader.dll doesn't exist`。
  根因：Tauri 的 **codegen 在编译前就校验 resources 路径存在**，而该 dll 是链接阶段产物。
- 正确做法：dll 作为**仓库内副本** `src-tauri/WebView2Loader.dll`（160KB，与构建产物 sha256 一致），
  resources 指向它，与构建顺序无关。
- 验证手段：删掉 `target/release/WebView2Loader.dll` **模拟冷构建**再打包 → 包内仍含该 dll。
- 回归断言补强：源路径不得含 `target/`，且 `src-tauri/<源>` 必须存在（防再次复发）。
- 最终发布 **v0.2.2**（v0.2.1 tag 的构建失败、无 Release 产物）：
  Release 已成功，远端安装包下载回来解包确认含 dll（8 个文件）。
  ⚠️ 教训：**本地打包成功 ≠ CI 能成**，凡 resources 指向构建产物的都要按冷构建校验。
- ⚠️ 又一次 `windres: preprocessing failed` 瞬时故障（pre-push 的 cargo test），
  重跑即过——**不要**为此改 .rc 或图标（B43 已记过）。
- 排查套路值得复用：**「装好起不来」= 先看 exe 导入表 → 再解包安装包比对文件清单 →
  用干净目录启动验证**，三步都能在沙箱里做完。

### 顺手修掉的真 bug：会话恢复一直是坏的

为了拍到「左源码 + 右预览」，把 `viewMode: "preview"` 写进 session.json，
结果**右侧仍是源码**；而且应用落盘回写后 `view_mode` 变成 `null`。

根因：Rust `TabSession` / `SessionState` 只有 `#[serde(default)]`、字段是 snake_case，
而 `src/ipc/api.ts` 与 `main.ts` 读的是 camelCase（`st.viewMode` / `sess.activePanel` /
`st.cursorLine`）。**两个方向同时坏**：

- 前端 → Rust：camelCase 被当未知字段丢弃 → 落盘永远是 `null`；
- Rust → 前端：`view_mode` / `cursor_line` 对不上 TS 的 `viewMode` / `cursorLine` → 永远 `undefined`。

用户可见后果：**重启后光标回到第 1 行、Markdown 预览模式丢失、活动面板错位**，全程不报错。
一直没被发现的原因：会话相关测试全部 mock 了 `loadSession`，只走 JS 侧，serde 这层从没真跑过。

修法（B49）：

1. 三个结构体加 `#[serde(default, rename_all = "camelCase")]`（与 `TabInfo`/`OpenedFile` 一致）；
2. 多字字段加 `#[serde(alias = "cursor_line")]` 等，兼容旧版本落盘的 snake_case；
3. 在 `session/mod.rs` 内联 `#[cfg(test)] mod tests` 补**过 serde 的 round-trip 测试**：
   能读 camelCase、落盘是 camelCase、旧 snake_case 仍可读。
   教训已写进 `ARCHITECTURE.md` §8 首条。

顺带记牢：**`cargo build --release` 出来的 exe 是 devUrl 变体**（`custom-protocol` 只有
`tauri build` 会开），跑起来是「无法访问此页面 / ERR_CONNECTION_REFUSED」；
截图与交付一律用 `tauri build`（增量约 1m45s）。已写进 `BUILD-ENV.md`。

## B50 启动白屏优化（10:00–10:50）

**需求**：用户反馈 exe 打开时先白屏一下，希望消除并提升启动速度。

### 根因与修法

窗口在 WebView2 画出第一帧之前，客户区由 Chromium 用**纯白**填充；前端要走完
`await loadSettings()` → `await restoreSession()` 才有东西可画。修法两层：

1. **Rust 预渲染底色**（`src-tauri/src/main.rs`）：`setup()` 里
   `win.set_background_color(Some(boot_background(&win)))`；
   `boot_background()` 读 `session::load().theme`（dark/light 直接定，system 问
   `win.theme()`）。常量 `BG_DARK = #1b1d1f` / `BG_LIGHT = #ffffff` 必须与
   `global.css` 的 `--bg` 一致。
2. **tauri.conf.json**：主窗口加 `"backgroundColor": "#1b1d1f"`（创建窗口时的兜底，
   setup 阶段再按主题纠正）。
3. **index.html 内联首屏样式+脚本**：`<style>` 给 html/body 深浅两套底色 +
   `@media (prefers-color-scheme: dark)` 兜底；`<script>` 同步读
   `localStorage["litepad.theme"]`（`theme.ts` 的 applyTheme 已写入）设好
   `data-theme`，让模块脚本还没跑完时首帧就是主题色。
   → 四处配色（conf / main.rs / global.css / index.html）必须一致，
     `tests/regressions.test.ts` 有断言守护。
4. **会话恢复并行读盘**（`restoreSession`）：原先逐个 `await openFile()`，N 个文件
   N 次串行往返；改为先收集 `pending` 再 `Promise.all` 并行预取进 `openedCache`，
   组装循环读缓存。总耗时≈最慢的那一个。

### ⚠️ 推翻自己：visible:false 方案的真正问题

先试了「`visible:false` + 前端就绪后 `show()`」，实测窗口一直空白、IPC 全无，
当时结论写成「visible:false 会让 WebView2 不加载页面」——**这个结论是错的**。
后来发现真凶是 **WebView2 用户数据目录损坏**
（`%LOCALAPPDATA%\com.litepad.app\EBWebView`，反复 `Stop-Process -Force` 杀进程
造成的），把该目录改名后 IPC 就恢复了。

visible:false 方案被否的**正确理由**是风险不对称：窗口是否出现完全取决于前端能否
跑完 bootstrap，一旦前端卡住（实测真实发生过）用户就是「点了图标什么都没有」，
比白屏严重得多。底色方案窗口永远在、永远不是白板。
`regressions.test.ts` 的断言就是防止 visible:false 复活。

### 实测数据（沙箱，`%TEMP%\whiteline.py` 高频采样）

- 129ms 出现窗口，首帧 RGB=(20,20,20)（深色过渡态），160ms 起稳定 (27,29,31)=#1b1d1f；
  3 秒内 15ms 间隔采样**全程无白色**。

  整组移除；`checkRow()` helper 与 `PreferencesDialogOptions` 里的
  `wordWrap/onWordWrap/autosave/onAutosave/onKeymap` 五个字段一并删除。
- **功能只是搬家**：自动换行在「查看」菜单、自动保存在「文件」菜单、快捷键在
  「设置」菜单（`label: "快捷键…"`）——回归断言同时检查「弹窗里没有」与「菜单里有」，
  避免以后被误删成砍功能。
- 断言写法：检查 `"自动换行"`（带引号的字面量）而不是裸词，否则会撞上源码注释里的同名描述。

### 3. 主题按钮三态（本次最需要想清楚的一处）

- 三档：浅色（太阳）/ 深色（月亮，`.tool-btn-active` 高亮）/ 跟随系统（半明半暗圆，
  新增 `followSystem` 图标）；档位写进 `btnTheme.dataset.themeMode`，title 与
  `aria-label` 同步成「主题：X（点击切换为Y）」；切档后状态栏回执「主题：X」。
- **循环顺序跟着系统偏好走**：`themeCycle()` 返回 `system → 与当前生效相反的显式档 → 另一档`。
  理由：三态里「显式档 → system」这条边是否翻转取决于系统偏好，**数学上不可能**
  让三条边都保证翻转；把 system 的下一档设成「与当前生效相反」的显式档后，
  默认档（system）出发的第一下点击必定翻转——正好是老 bug
  「深浅色按钮要点两下才生效」的原始场景。
- 测试契约随之改写：不再断言「每次都翻转」，改为
  ① 每点一次必换档且图标必变（可见反馈）；
  ② 从 system 出发第一下必翻转；
  ③ 一轮三档循环里两个显式档相邻，浅⇄深必翻转。
- ⚠️ **档位是跨用例共享的模块状态**：`smoke.bootstrap.test.ts` 里加了
  `resetThemeToSystem()`，凡依赖「点一下必然翻转」的用例先归位，
  否则前一个用例把档位留在「浅色」时，下一个用例第一下会走到 system
  （jsdom 偏好浅色 → 外观不变）而无辜失败。
