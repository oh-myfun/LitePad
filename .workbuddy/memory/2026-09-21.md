## B89 跨窗口拖拽：途中只预览，松手才提交（用户报的毛病）

用户原话：卫星窗口的标签/面板拖入拖出窗口时没有预览，一旦拖入或拖出就**立马生效**，
操作不连贯（想把窗口 A 的标签拖到窗口 B 的面板 A，经过面板 B 就被自动合入）。

### 根因
`splitview.ts` 的 `onTabDragMove` 一判定 `outsideWindow` 就 `finishTabDrag()` +
`onDragOutOfWindow(...)` —— **副作用发生在拖拽途中**，而不是松手时。于是：
· 主窗口拖出：鼠标还没松手就弹出新窗口；
· 卫星窗口拖出：指针擦过主窗口就整组合入，没法挑落到哪块面板。

### 改法
- 拖拽层（splitview）：出界只做三件事 —— 记 `tabDrag.outOfWindow`、清掉**本窗口**的落点
  痕迹、调 `onDragOutside`（通知宿主广播指针位置）。**不收尾、不搬运**。
  `onTabDragEnd` 见 `outOfWindow` 才 `onDropOutOfWindow`。
- 新增 `src/shell/windowdrag.ts`：跨窗口协议
  hover（广播坐标）→ 各窗口自己判定命中并渲染预览 → release（广播坐标）→
  命中的窗口 claim → 发起窗口 `emitTo` 定向发正文 → end 清场。
- 宿主（main.ts）：`dropTabsOutOfWindow` 先问「有没有别的窗口接手」（等 200ms），
  有 → 定向投递 + 本地摘标签（主窗口 `remoteTabLocally` 留隐藏实例 / 卫星 `detachLocally`）；
  没有（扔在桌面）→ 回落到旧语义（主窗口开新窗、卫星交回主窗口）。
- 影像贴边：出界后 ghost 若照坐标走会整个跑出客户区（看不见），改为 clamp 到边缘露一条。

### 三条不变量（写进 `ref/multiwindow.md` §9.4）
1. **Windows 隐式鼠标捕获**：鼠标按下后指针掠过别的窗口时，那个窗口**收不到任何鼠标
   事件**，发起窗口反而能继续收 mousemove/mouseup。所以「指针压在哪块面板上」只有目标
   窗口自己知道 → 必须走 IPC。
2. **正文绝不广播**：`emit` 是广播，每个窗口都收到一份完整 payload；标签快照带正文，
   几十 MB × 窗口数。所以 release 只带坐标，claim 之后才 `emitTo` 单独发。
3. **先挂 claim 监听、再广播 release**：反过来的话接手方的回答可能早于监听就位，
   这一拖只能干等超时再回落成「开新窗口」——表现为「明明拖到了另一个窗口却还是新建了」。
4. 坐标口径：一律**逻辑像素**（`outerPosition/outerSize/innerSize` 都是物理像素，
   必须除以 `scaleFactor`，高 DPI 屏上否则整体偏一倍）；几何一次拖拽问一次并缓存。

## 拖拽影像跟出窗口的可行性调研（wry 实证，未动代码）

用户问：「Rust 上有没有能实现和 VS Code 一样的效果（既拖文件进窗口，又拖标签有影像）」。

- **结论：能做，但不是配置开关层面的事。** 硬证据（读本地 `wry-0.55.1` 源码）：
  · `wry/src/webview2/mod.rs:152` 在有 drop handler 时执行 `controller.SetAllowExternalDrop(false)`
    （注释原文 "Disable file drops, so our handler can capture it"）—— **页内 HTML5 拖放失效的真凶**；
  · `wry/src/webview2/drag_drop.rs:50-73` 用 `EnumChildWindows` 找到 WebView2 的子窗口并
    `RevokeDragDrop` + `RegisterDragDrop` 覆盖其拖放目标；
  · 该 target 只处理 `CF_HDROP`，其它格式一律 `DROPEFFECT_NONE`（禁止光标）。
  · `dragDropEnabled: false` 时 wry 不碰 `AllowExternalDrop`（默认 true）→ 页内 DnD 恢复，
    但拖文件进窗口只拿得到内容、拿不到路径。
- **三条路线（对比表已给用户）**：
  B 置顶穿透浮层窗承载影像 —— 保留 `dragDropEnabled: true` 与 B89 IPC 协议，只把影像搬出 DOM；
    影像可跟出窗口并压在其它的应用之上。改动集中在影像层，风险最低。**当前推荐**。
  C Rust 自建 `DoDragDrop` + `IDragSourceHelper` 出系统影像，并接管 wry 的 drop target 收落点
    （保留 CF_HDROP 转发）—— 最接近 VS Code，但 unsafe COM 量最大，且要和 wry 的注册时序抢。
  D `dragDropEnabled: false` 换回 HTML5 DnD（Chromium 自带跟手影像，跨窗口走自定义 MIME）+
    用 `WH_MOUSE_LL` 低级鼠标钩子在左键按下时抢注 `CF_HDROP`（yyzTools 的生产做法，撤销要延迟
    ~150ms，否则最后一刻 drop 落空）—— 要重写 B89/B90 拖拽层，且**必须先 spike 验证
    WebView2 的 HTML5 拖拽影像是否真跟出窗口**。
- tauri 2.11.5 已具备路线 B 所需 API：`set_ignore_cursor_events` / `set_always_on_top` /
  `set_skip_taskbar` / `set_shadow` / `set_focusable`。
- 🎉 **推送线路恢复**：`github.com:443` 之前不通，但 `ssh.github.com:443` 通、`git@ssh.github.com`
  认证通过（`oh-myfun`）。备用：`git push ssh://git@ssh.github.com:443/oh-myfun/LitePad.git main --follow-tags`。
  本次已用 https 正常线路重试 `git push origin main --follow-tags`（含 v0.10.0/v0.10.1 两个 tag）。

   与载荷 `{paths, position}` 与我们现有 `main.ts` 的 `onDragDropEvent` 完全兼容**。
   ⚠️ 但只能抄不能依赖：0.1.0 / 17 次下载 / 单人 / 无文档；**发布的注入脚本多一个 `}`**
   （`src/desktop.rs:24` 的 `}}`，README 里同一段是平衡的）→ 脚本语法错误，`ExecuteScript` 的错误又被
   `let _ =` 吞掉，按发布版大概率根本不生效。→ **把这 130 行抄进 `src-tauri`**（外加 hover 事件扩展）。
2. 拖拽层（若要换成 HTML5 DnD）：`@atlaskit/pragmatic-drag-and-drop` 3.1.0（Trello/Jira/Confluence 在用，
   2026-08-29 仍在更新），external adapter 覆盖「从其它窗口开始的拖拽」。
3. 原生拖拽影像：`drag` 2.1.1 / `tauri-plugin-drag` 2.1.1（CrabNebula，2026-05 更新、12 万下载）=

## B91 第二步：标签拖拽换回 HTML5 DnD（影像交系统绘制，跟出窗口）

用户诉求原话：「标签拖动时，要像 vscode 那样有一个 tab 随光标移动的效果」——B64–B90 那套指针
编排的影像是**本窗口的一个 DOM 浮层**，指针一越过窗口边界就看不见了（B90 刻意不夹取，于是
「拖出去影像就消失」）。方案二把关掉 `dragDropEnabled` 之后复原的 HTML5 DnD 用回来。

### 实现
- **新建 `src/shell/tabdnd.ts`（传输层）**：`TAB_MIME` 私有格式、`encode/decodeTabDrag`
  （逐字段校验，`v` 必须为 1）、`isTabDragData`（只看 `types`）/`readTabDragPayload`（只有
  `drop` 里能读 `getData`）、`startTabDrag(e, payload, image, anchor)`（写 MIME +
  `effectAllowed="copyMove"` + **离屏挂 body → `setDragImage` → 立刻摘掉** + 挂 `body.tab-drag-active`）、
  `installTabDnd(cfg)`（页面级 dragenter/over/leave/drop/dragend + claim/payload 监听）。
  影像**必须已渲染过**才能拍出图（detached / `display:none` 都会拍成空图）→ CSS `.tab-drag-image`
  只用 `position:fixed; left/top:-10000px` 挪出屏。
- **跨窗口交接（替换 B89 的广播协议）**：drop 在目标窗口触发 → 目标 `emitTo` 源窗口
  `EVT_TAB_CLAIM`（带 `dragId`）→ 源窗口配对后 `emitTo` `EVT_TAB_PAYLOAD`（正文，只发给它一个）
  + 本地 `relinquish`。**删掉一整套**：广播指针坐标、每窗口几何缓存与命中判定、200ms 抢单超时、
  hover 节流；`src/shell/windowdrag.ts` 整个删除。落点（spot）只在目标窗口内算一次、**不过 IPC**。
- **回落（扔桌面）**：`dragend` 的 `screenX/screenY` 是唯一还带最后位置的时机（拖放循环期间
  页面收不到任何指针事件）→ `desktopSpotOf` 挡掉非有限值与 `(0,0)`，拿不到就让系统自己摆。
  ⚠️ 源窗口的 `source` 要等 `CLAIM_GRACE_MS = 300` 宽限到期才清 —— 认领是 IPC 往返、必然晚于
  `dragend`；不等的话每次成功的跨窗口拖拽都会同时被当成「扔桌面」→ 标签复制成两份。

### 两个实现真 bug（都是新增回归用例才暴露）
1. **本地落点收尾**：落点常重建面板 DOM，源标签元素随之脱离文档 —— 而 `dragend` 是派发到

2. **`source` 生命周期**：原想用 `local` 字段标记本地落点，但该字段永远等不到 dragend 去清。

## B91-2 两个回归修复（用户报，均在 v0.11.0 交付后暴露）

用户原话：「窗口内和窗口间拖动 tab 或面板时**没有标签影像了**。拖动标签会导致**面板中其他
文档里插入文件名**，要修复。」两条都是 B91-2 首交付引入的，根因**互相独立**。

### 回归① 拖标签完全没有影像
- **根因**：Chromium 是在 `dragstart` **派发返回之后**（`DragController::StartDrag`）才读
  元素拍快照的；`startTabDrag` 里同步 `image.remove()` → 快照时元素已 detached → 系统拿不到图。
  影像由系统绘制，所以**窗口内与跨窗口同时失效**（单标签与整组都一样）。
- **修**：`setTimeout(() => image.remove(), 0)`（对齐 VS Code `applyDragImage`）；顺手在起手处
  清掉上一轮残留的 `.tab-drag-image`。
- → `pitfalls/0093-dnd-dragimage-sync-remove.md`

### 回归② 拖标签把文件名插进别的文档正文
- **根因（两处叠加，缺一不可）**：
  1. `startTabDrag` 里 `dt.setData("text/plain", payload.name)` —— 落点的 contenteditable
     编辑器看到可读文本，按「有人拖了一段文本进来」插进正文；
  2. `installTabDnd` 的监听挂在**冒泡阶段** → 编辑器自己的监听**先**收到 `drop` 并插入，
     我们的处理器后到，拦得住「落在哪」拦不住「正文被改」。
  跨窗口更彻底：自定义 MIME 未必跨过 WebView2 进程边界 → `getData` 读不出 → 旧代码直接
  `return`，**连 `preventDefault()` 都没有** → 浏览器自己插。
- **修**：① 删掉 `text/plain`（标签拖拽是内部协议，不对外给正文 —— 这同时是跨窗口的兜底：
  没东西可插）；② 监听全改 `{ capture: true }` + `stopPropagation`（`claim()` 辅助收敛，
  只对标签拖拽生效，文件拖入原样放行给 `filedrop.ts`）；③ `onDrop` 先无条件 `claim`
  （`preventDefault`）再读载荷，读不出也拦默认动作 + `onWarn` 记日志。
- `startTabDrag` 的 `payload` 去掉 `name?` 字段；`tabstrip.ts` 调用点同步去掉 `name: t.name`。
- → `pitfalls/0094-dnd-textplain-leaks-into-editor.md`
