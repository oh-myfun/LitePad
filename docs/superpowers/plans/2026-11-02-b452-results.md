## 真机抓到的两个病灶（台子全绿也不会自己浮出来的那种）

### 1 · Flowchart 画成一条 56px 宽的窄图

**病根**：flowchart.js 的节点尺寸来自 raphael 的 `text.getBBox()`，而**脱离文档的节点一律量到 0×0**。预览臂在 CM6 `toDOM()` 里就发起渲染，那一刻整块 widget DOM 还没进文档 ⇒ 每个节点只剩内边距那么宽。事后把它 append 进文档**救不回来**：尺寸在 `drawSVG` 那一刻已经算死。

A/B 取证（`.tmp/b452-flow-spike.html`，真浏览器里量同一份源码）：

| 动笔时的状态 | svg 宽 | 每个 `<text>` 的宽 |
|---|---|---|
| 已挂进文档 | 132.7 | 28 / 56 / 35.8 / 28 / 21.8 / 15.8 |
| 脱离文档 | 79 | 0 / 0 / 0 / 0 / 0 / 0 |
| 脱离文档画完再 append | 79 | 28 / 56 / …（已经晚了） |

**修法**：`measuringMount(root)` —— 先等这块 DOM 进文档（上限 250ms，超时退到 `body` 照样画，图不许永远空着），画进一格 `.md-diagram-measure`（绝对定位甩出屏幕外：参与布局但不占位置，因而不搅动 CM6 的块高测量），画完把成品 `<svg>` 挪进 host、测量格当场撤掉。

**判据**：动笔那一刻 `container.isConnected` 必须为真；测量格画完不在文档里留残渣；那条 CSS 不许写成 `display:none`（写了就等于白测）。

### 2 · PlantUML 显示的是服务器自己的错误文案

`plantumlImageUrl` 在编码串前面多写了一个 `~1`。那是 PlantUML 的**密文前缀**：服务器换一套解码器，回来的是 200 + 一张合法 SVG —— 画的是「This URL does not look like HUFFMAN data」。curl 同一份源码两种拼法：

| URL 尾巴 | 回来的东西 |
|---|---|
| `/svg/<编码>` | 真图（含 `client` / `app` / `db`，233×94） |
| `/svg/~1<编码>` | 错误图（790×246，正文是 HUFFMAN 那句） |

**两层假绿**，都记进 pitfalls：

- **判据没鉴别力**：真机原来只问 `naturalWidth>0 && complete` ⇒ 错误图照样过。改成探针进程抓同一个 URL、读响应体：含 `<svg`、不含 `bad URL`/`HUFFMAN`/`Syntax Error`、且含夹具那几个元素名。（页面内 `fetch` 会被 CORS 挡，所以放 Python 侧；plantuml.com 对默认 `Python-urllib` UA 直接 403 ⇒ 探针得报一个浏览器 UA。）
- **测试重抄了生产的构造**：URL 形状被抄在两处断言里，`~1` 就跟着两处一起绿。现在两处都比 `plantumlImageUrl(...)` 同一颗，只留一条独立断言盯「前面不许有 `~`」。

## 已知边界（选型带来的，不是漏修）

- **PlantUML 是服务器画好的图，不跟深色档**：它自带白底，深色主题下是一张白板（真机截图确认）。这是「在线服务器」那条拍板的直接后果；要深色得换本地 jar/自建服务并让它吃主题色。**用户 2026-11-02 拍板：保持现状**（与 vditor / 多数在线渲染方案一致）。
- **用户源码写错时也是同一张错误图**：客户端分辨不了（跨域读不到响应体），只能原样显示。vditor 同样如此。
- **大文档档位（`bigDoc`）不自动画任何图**，与 Shiki 同一颗闸，留源码块。
