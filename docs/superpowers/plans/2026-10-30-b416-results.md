# B416 结果 · 滚轮把源码滚到顶时预览也要停在顶部（与大纲跳第一个标题同口径）

用户口径（2026-10-30）：

> 同步滚动时，鼠标滚轮滚动源码到顶部和通过大纲点击第一个标题跳到顶部，前者预览模式的位置不在顶部，
> 后者在顶部，滚动位置更一致。

## 根因：文首那一发走了「按字符对齐」，而大纲那一发走 `setV`

两条路给对栏的落点由不同分支决定：

| 路径 | 载荷 | 对栏动作 |
| --- | --- | --- |
| 大纲点第一个标题（`toc.ts → syncTo(docId, line)`） | 只有 `v=1.00`，`at=null` | `setV(1.00)` ⇒ `scrollTop = 块顶 = 0` |
| 滚轮滚到顶（`scroll` → 账本判「用户滚动」→ 帧广播） | `v=1.00` **+ `行首@0`** | `setVAt(0)` ⇒ `scrollTop = coords.top - 容器顶` |

`setVAt(pos)` 的对齐基准是 `coordsAtPos(pos).top`（**字符盒顶**），不是行块顶；而预览面
char 0 是标题行被折起来的 `#` 号，CM6 给它的盒顶比行顶低一截 —— 真机实测
`setVAt(0) ⇒ scrollTop 29.33`（`.cm-content` 上内距 14 + 标题盒内偏移 15.33）。
于是同一份文档、同一个「文首」，两条路一个停在 0、一个停在 29.33。

日志证据（修前，`.tmp/b352-check/config/logs/litepad.log` 2026-10-30 01:08:25）：

```
帧广播 doc=1 驱动=[P1:editor] v=1.00 行首@0 目标=1
广播写[P2:editor] 目标=1.00 行首@0 落点=1.56        ← 预览停在 29.33px
```

对照大纲那一发（01:08:28）：`外发 doc=1 v=1.00`（**无行首**）→ `广播写[P2:editor] 落点=1.00`，
两侧 `scroll` 回声 `px=0.00`。

## 修法：`at === 0` 走 `v`

文首没有「上一行」可对 —— 两侧各自的**绝对顶部**（各露各的 `.cm-content` 上内距）才是共同答案。
所以把「按字符对齐」的适用条件收成 `at > 0`，两处同口径：

- `src/sync-scroll/coordinator.ts` `writeTo()`：`const byPos = at !== null && at !== undefined && at > 0 && !!e.anchor.setVAt;`
- `src/sync-scroll/wire.ts` `landVisibleSideAtV()`：`const byPos = at !== null && at > 0 && !!face.anchor.setVAt;`

`at > 0` 之外的逐行对齐（B300）一个字节没动：中途位置仍按字符对齐，行为与修前一致。

⚠️ 没有把规则塞进 `EditorScrollAnchor.setVAt(pos)` 内部，是因为 `landVisibleSideAtV` 的「收口」
判据是 `topPos() === at` —— 文首落在 `scrollTop=0` 时容器顶边在上内距里，`topPos()` 的读数
不可靠；走 `setV` 这一支的收口判据是 `|落点 − v| ≤ 0.05`，确定性成立，不会触发「藏起来重试」。
