## ③ 计划 §⑤ 那四个洞，逐条交代

1. **`viewMode === "split"` 在装饰臂没有右格** —— **维持现状，不新增 split**。
   `viewMode` 的类型只有 `"source" | "preview"`（`src/core/app-state.ts:53`）；恢复会话时旧版的
   `"split"` 一律映射回 `source`（`src/session/rebuild.ts:325`）；产品里没有任何路径写它。
   一颗 view 不可能同时当两面用，这条洞从此只存在于手工造的老会话。
2. **大文件 md 落进装饰格 ⇒ 预览一片裸文本、无说明** —— **已修**（`af5bc4f`）。
   体积闸的语义是「这一份文档此刻开不开装饰」，所以换成**每格每次现问**；挡下时同一格就地
   换到派生那一臂（它本来就会给「已停用自动预览」的提示、也在用户显式切预览时手动渲染）。
   为什么不学 InkNote 一臂到底：它的 `previewSyntaxTree` 是 `ensureSyntaxTree(state, doc.length, 100)`
   （`src/editor/codeFence.ts:43`）—— 全文同步 parse，100ms 预算，大文档正是它的代价；
   为什么不学 VS Code：它的降级在 model 层（`src/vs/editor/common/model/textModel.ts:189-193`，
   20MB / 300K 行 / 256M 字符 ⇒ 关 tokenization），编辑器与预览照渲染。**两家都不出现「预览一片裸源码」**，
   而 LitePad 的 >2MB 降级是既有产品策略 ⇒ 只换臂，不改策略。真机 M-15a..d 四组读数在 ④。
3. **只读文档在 A 格被写、B 格停在预览档（有锁）：`syncDocInstances` 那一发被 B 格的
   `transactionFilter` 丢掉 ⇒ B 显示陈文。** —— **本轮不动，记在这里**。要碰到它得同时
   满足「只读 + 同一文档多实例 + 其中一格在装饰预览档」，本轮没有新证据说它变严重。
4. **换档时的落位与重注册，jsdom 量不出像素** —— **真机判绿**：M-15d（派生预览**全新挂载**
   后回到滚轮推到的 4516，一位不差）+ M-18a/b（同格换档 42663 → 42621 → 42707，三次都落在
   底部锚 v = 0.999–1.000）。判据按**账本的 v** 问，不按像素：两档块高不同（sh 差 85px），
   Ctrl+End 在装饰档还会留末块底那 43px 留白 —— 那都不是「换档漂移」。

## ⑤ 性能：同一把尺子，把「冷」和「暖」分开

同一台机器、同一份 181KB 夹具、同一条 RAF 采样器（`H.keystroke_frames`，20 击键一发），
两臂都在 `H.foreground()` + `RAF 25–26 帧/400ms` 自证之后才量：

| 臂                | 冷发    | 暖 1   | 暖 2   | 暖 3   | 暖机中位数 |
| ----------------- | ------- | ------ | ------ | ------ | ---------- |
| 对照（deco off）  | 16.67ms | 8.28ms | 5.51ms | 4.13ms | **5.51ms** |
| 装饰（deco on）   | 16.67ms | 8.28ms | 5.51ms | 4.13ms | **5.51ms** |

- **两臂逐发相同（连帧数都几乎一致）**：装饰面没有把击键拖出同一条轨迹。
- 冷的第 0 发两臂都恰好落在 16.67ms —— 那是「文档刚打开、第一批键触发首测/首排版」的代价，
  与装饰无关。**这也解释了这一轮之前的四次单发读数**（16.67 / 17.27 / 19.64 / 23.89ms，
  比值 0.85–1.20）：量的是冷发 + 机器抖动，不是装饰的成本。
- 结论口径：**16.7ms 这条绝对阈值在单发口径下没有鉴别力（对照臂也时过时不过）；同尺、去冷发
  之后，装饰臂 = 对照臂**。阈值一个字没改，判据改成「暖机中位数 ≤16.7ms + 两臂比值 ≤1.1」。

## ⑥ 与 InkNote 的已知差集（累计，都是有意为之）

- **没做**运行中的 InkNote 像素并排：数值判据直接从它的样式表解析（比截图硬），观感对照用

## ⑩ B400 标签拖到外部应用（v0.24.51）

用户原话：「标签支持拖拽到vscode等其他应用中打开对应文件」。两轮追问把口径钉死：

- **只要求外部软件收到文件**；LitePad 这一侧「行为不变，只是拖到别的应用不产生行为」——
  即拖出去之后，LitePad 不关标签、不改状态、也不接管那个落点。
- 脏文档：**先保存再拖**（用户选项，不是「拖未保存的内容 / 取消」）。

### ⑩-1 为什么必须走原生 OLE

Web 侧拖拽的 `DataTransfer` 只能带字符串、blob 和**由用户选中产生的** `File`，JS 造不出
带真实磁盘路径的 `File`。而 VS Code 的落点只认 `Files` / `CodeFiles` / `ResourceEditors`
三类（`E:\Project\vscode` 里 `editorDropTarget.ts:629` 的过滤），纯 `text/uri-list`
不进门。所以外部打开这条路只有一条：由 Rust 侧起一次**原生 OLE 拖拽**，数据对象里放
`CF_HDROP`（Windows 的「拖出去的是文件」标准格式），落点是谁都能收。

### ⑩-2 手势切分

- **平拖不变**：重排 / 跨面板 / 跨窗口 / 拖出成新窗口，全部还是原来那条 HTML5 路径。
- **Ctrl + 拖动**：只有当那个标签背后是一份**已存盘的真文件**（`t.path` 非空）时，
  `dragstart` 里 `preventDefault()` 掉 HTML5 拖拽，改走 `dragTabAsFile`。没路径的
  「未命名」标签按平拖处理（它没有东西可给外部）。
- 脏文档先 `saveDocCore(doc, tab, false)`；保存失败就**不起拖**、只 warn。
  保存可能把「未命名」落成真路径，所以拖之前**重新读一遍 `doc.path`**。

### ⑩-3 实现

- **`src-tauri/src/filedrag.rs`（新）**：`#[implement(IDataObject, IDropSource)] TabFileDrag`
  - `GetData` 供两样：`CF_HDROP`（`DROPFILES` 头 + 宽字符路径 + 双 NUL，头按
    `packed(1)` 20 字节）与 `"Preferred DropEffect"` = `DROPEFFECT_COPY`（4 字节）。
    其余格式一律 `DV_E_FORMATETC`；`QueryGetData` 对这两样 S_OK；`EnumFormatEtc` 走
    `SHCreateStdEnumFmtEtc`。
  - `QueryContinueDrag`：Esc → `DRAGDROP_S_CANCEL`；左键已松 → `DRAGDROP_S_DROP`。
  - 模态：`DoDragDrop` 必须跑在**拥有窗口的 UI 线程**上，`start_file_drag` 里经
    `run_on_main_thread` 进。进之前 `normalize_paths`（绝对 + 存在 + 是文件）与
    `GetAsyncKeyState(VK_LBUTTON)` 守卫（保存耗时可能把「手已经松开」拖成一次幽灵拖拽）。
  - OLE 初始化：`OLE_READY: AtomicBool` 进程内只做一次，**永不 `OleUninitialize`** ——
    windows 0.61 把 `OleInitialize` 包成 `Result`，`S_FALSE`（别人已经初始化过）也是 Ok，
    成对调 `OleUninitialize` 会去减别人的引用计数。
  - 日志：起拖 `[filedrag] 拖出 N 个文件`，收尾 `[filedrag] 拖出结束：hr=… effect=…`
    —— 后一条是本轮真机自证的钥匙（见 ⑩-5）。
- **windows 0.61 的四个坑**（都写进 Cargo.toml / 代码注释了）：`BOOL` 是
  `windows::core::BOOL` 不是 `Win32::Foundation`；`FORMATETC.cfFormat` 是 `u16`；
  `HWND` 是 `*mut c_void`；`#[implement]` 宏展开里写的是 `::windows_core::` 路径 ⇒
  **必须直接依赖 `windows-core = "0.61"`**（只用 `windows` 的 re-export 编不过）。
  另：`*mut c_void` 不 Send，`run_on_main_thread` 的闭包只能带 `hwnd as usize` 进去再转。
- **`src/io/filedrag.ts`（新）**：`canDragTabFile` 判路径；`dragTabAsFile` 做
  「脏则先存 → 重读路径 → `invoke("start_file_drag", { paths: [path] })`」。
- **接线**：`tabstrip.ts` 的 `dragstart` 加 `e.ctrlKey && t.path && cb.onDragFileOut` 分支
  （`e.preventDefault()` 后 return，平拖那支不碰）；`splitview.ts` 把
  `onDragTabFile` 传成 `onDragFileOut`；`lifecycle.ts` / `render.ts` 两处
  `renderSplitview` 的 callbacks 里各接一条 `dragTabAsFile`。
- README 的拖拽体系一节补了第三条路径（`docs/architecture.md`）。

### ⑩-5 台子的五次自伤（都记在 pitfalls 里）

1. 第一次点击落到**标签 B** 上 ⇒ 加 `SetProcessDPIAware`；仍不对，但 `elementFromPoint`
   证明 CSS→物理坐标换算是对的（不是坐标的锅）。
2. 点击/拖动被 **`WM_MOUSEACTIVATE` 吞掉**（窗口不在前台，`SetForegroundWindow` 也被系统
   拒）。随后独立探针查明当时桌面正处 **锁屏界面**（`isTrusted` 的 mousedown 计数 = 0）——
   真实输入根本进不来。于是先做**边界台**（合成事件 + IPC 直调）把路径证明干净。
3. 换到真拖后 `SetWindowPos` 静默失败：`HWND_TOPMOST` 当 Python int 传被截成 32 位 ⇒
   设 `argtypes`/`restype` 并传 `ctypes.c_void_p(-1)`，两个窗口才真正摆到位。
4. 窗口摆好了副本还是不来 —— **靠新加的那条 `effect=` 日志**才看清：
   `hr=0x00040100`（确实 drop 了）但 `effect=0`（落点不在任何目标上）。
   根因是相对位移的 `mouse_event` 走**指针加速**，一路过冲。
5. 改 `MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_MOVE`（0..65535 归一化）+ 落点前 0.9s 停顿，
   读 `cursor before drop (1890,840)` → `effect=1` → 副本落地。**收口**。

### ⑩-6 边界（有意没做）

- **只支持单标签**：多选批量拖出没有做（当前标签栏也没有多选语义）。
- **只 COPY**：`Preferred DropEffect` 写死 COPY，不做 Ctrl=复制 / Shift=移动的切档；
  落点自己按它的规则处置（资源管理器同盘拖放仍可能移动 —— 那是落点的行为）。
- **「未命名」标签落回平拖**：没有文件可给。
- **拖回 LitePad 自己 = 普通的文件拖入打开**（dropbridge 那条既有路径）——「拖到别的应用
  不产生行为」指的是 LitePad 不在外部落点上做额外动作，不是屏蔽自家拖入。
